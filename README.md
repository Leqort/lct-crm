# CRM ИТ Школы Ростелекома — ядро данных (SPEC-01)

Backend-фундамент CRM, автоматизирующей взаимодействие ИТ Школы Ростелекома с вузами.

**Что реализовано в этой части:** схема БД и миграции, CRUD справочников, карточки
взаимодействий, двухфазный импорт каталогов из Excel, аудит-лог, ролевой доступ.

**Чего здесь нет (другие спеки):** workflow-движок и переходы по этапам (SPEC-02),
отчёты (SPEC-03), интеграции с LMS и сайтом (SPEC-04). Модель данных и индексы под них
подготовлены — см. [Точки стыка](#точки-стыка-с-другими-спеками).

## Быстрый старт

### Через Docker

```bash
cp .env.example .env
docker compose up --build
```

### CI/CD: тестовый сервер

При push в `main` GitHub Actions выполняет `ruff`, `mypy` и `pytest`, собирает
образ на GitHub-hosted runner и публикует его в GitHub Container Registry
(GHCR). После этого по SSH на тестовом сервере выполняются `docker compose
pull` и перезапуск контейнеров. Dockerfile на сервере не используется и сборка
там не выполняется.

Файл [docker-compose.deploy.yml](docker-compose.deploy.yml) предназначен для
этого деплоя. На сервере один раз нужно установить Docker Compose v2, создать
каталог `/opt/lct-crm`, скопировать в него `.env.server.example` как `.env`,
заполнить секреты и выдать пользователю права на Docker:

```bash
sudo mkdir -p /opt/lct-crm
sudo chown -R DEPLOY_USER:DEPLOY_USER /opt/lct-crm
sudo usermod -aG docker DEPLOY_USER
```

Деплой также поднимает Caddy как reverse proxy. Caddy автоматически получает и
обновляет сертификаты Let's Encrypt для `DOMAIN` (API) и `KEYCLOAK_DOMAIN`
(Keycloak), а данные ACME сохраняются в Docker volumes. Перед первым деплоем
создайте DNS-записи обоих доменов на IP сервера и откройте входящие TCP-порты
`80` и `443` (UDP `443` — опционально для HTTP/3). Заполните эти переменные в
`.env`; `KEYCLOAK_ISSUER` должен использовать HTTPS-адрес Keycloak.

В настройках репозитория GitHub создайте Environment `test` и добавьте secrets:

| Secret | Значение |
| --- | --- |
| `DEPLOY_HOST` | IP или DNS сервера |
| `DEPLOY_PORT` | SSH-порт, например `22` |
| `DEPLOY_USER` | SSH-пользователь |
| `DEPLOY_SSH_KEY` | приватный SSH-ключ пользователя |
| `DEPLOY_PATH` | путь приложения, например `/opt/lct-crm` |
| `DEPLOY_REGISTRY_USERNAME` | GitHub username владельца токена |
| `DEPLOY_REGISTRY_TOKEN` | GitHub PAT с правом `read:packages` |
| `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan -p PORT HOST` (рекомендуется) |

`DEPLOY_KNOWN_HOSTS` можно временно не задавать: workflow получит ключ через
`ssh-keyscan`, но для постоянного использования лучше сохранить проверенный
host key. Для доступа к приватному GHCR-пакету на сервере нужен PAT с
`read:packages`; токен не записывается в репозиторий.

Поднимается PostgreSQL 16 и приложение. Миграции применяются автоматически в
entrypoint-скрипте контейнера, демо-данные засеваются при `SEED_ON_START=true`.

* Swagger UI — <http://localhost:8000/docs>
* ReDoc — <http://localhost:8000/redoc>
* Health-check — <http://localhost:8000/health>

### Локально (без Docker)

Нужны Python 3.12 и запущенный PostgreSQL 16.

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

```

### Проверка запросом

В dev-режиме личность передаётся заголовком `X-Debug-User` — UUID, `keycloak_id`
или email существующего сотрудника. Сид-скрипт заводит три учётки:

| keycloak_id | Роль | Видит |
|---|---|---|
| `seed-admin` | `admin` | всё + журнал аудита + мягкое удаление |
| `seed-manager` | `manager` | всё, может создавать и изменять |
| `seed-user` | `user` | только закреплённые за ним вузы |

```bash
curl -H "X-Debug-User: seed-manager" http://localhost:8000/api/v1/universities
curl -H "X-Debug-User: seed-user"    http://localhost:8000/api/v1/universities  # уже меньше
```

### Keycloak (AUTH_MODE=keycloak)

Локальный Keycloak поднимается вместе с остальным стеком:

```bash
docker compose up -d keycloak
```

При старте автоматически импортируется realm `crm` (`docker/keycloak/realm-export.json`):
публичный клиент `crm-api` (direct access grants включены — можно получать
токен паролем, без confidential-секрета) и три тестовых пользователя:

| Логин | Пароль | Роль |
|---|---|---|
| `kc-admin` | `admin123` | `admin` |
| `kc-manager` | `manager123` | `manager` |
| `kc-user` | `user123` | `user` |

Роль назначается прямо на пользователя как realm-роль и попадает в claim
`realm_access.roles` — именно оттуда её читает `_role_from_claims`. Локальная
запись в `users` создаётся/обновляется на лету при первом валидном запросе
(`_sync_user_projection`) — заранее заводить пользователя вручную не нужно.

Приложение запускайте с:

```bash
AUTH_MODE=keycloak uvicorn app.main:app --reload
```

`.env.example` уже содержит `KEYCLOAK_ISSUER` и `KEYCLOAK_JWKS_URL`, указывающие
на `http://localhost:8080/realms/crm` — это подходит, когда приложение
запущено на хосте (не в контейнере `api`), как в разделе «Локально» выше. Если
вместо этого используете контейнер `api` из docker-compose, он резолвит
Keycloak по имени сервиса (`http://keycloak:8080/...`) — переопределять
руками не нужно, это уже в `docker-compose.yml`. `KC_HOSTNAME=localhost`
у сервиса `keycloak` держит `iss`-claim токена одинаковым независимо от того,
с какого хоста Keycloak вызвали — иначе токен, выпущенный через
`localhost:8080`, не прошёл бы проверку `issuer` у сервиса, ходящего за JWKS
через `keycloak:8080`.

**Через curl** (быстро получить токен и проверить руками):

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/realms/crm/protocol/openid-connect/token \
  -d grant_type=password -d client_id=crm-api \
  -d username=kc-manager -d password=manager123 \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/universities
```

**Через Swagger** (<http://localhost:8000/docs>): при `AUTH_MODE=keycloak`
кнопка «Authorize» показывает форму OAuth2 password flow с полями
username/password (client_id уже подставлен) — Swagger сам получает токен у
Keycloak и подставляет его во все запросы. Никакого curl и ручной вставки JWT.

## Разработка

```bash
alembic upgrade head          # накатить миграции
alembic downgrade base        # откатить всё (проверено, отрабатывает без ошибок)
alembic revision --autogenerate -m "..."

pytest                        # тесты (нужна база crm_test)
ruff check .                  # линт
ruff format .                 # форматирование
mypy app                      # типы
python -m scripts.seed        # идемпотентный сид демо-данных и базового workflow
python -m scripts.export_openapi   # выгрузить OpenAPI в docs/openapi.json
```

Тесты требуют реального PostgreSQL: схема опирается на партиальные уникальные
индексы, `jsonb`, нативные enum'ы, trigram-поиск и GiST exclusion-ограничение —
SQLite это не эмулирует. База создаётся один раз за прогон и очищается между
тестами. Параметры подключения берутся из `TEST_POSTGRES_*` либо из обычных
`POSTGRES_*`, имя базы — `crm_test`.

## Модель данных

Общие правила для всех доменных таблиц:

* PK — `UUID` (`uuid4`), колонка `id`;
* `created_at` / `updated_at` (timestamptz, server default `now()`), `created_by` /
  `updated_by` — заполняются автоматически из контекста запроса;
* **удаление только мягкое** — `deleted_at timestamptz NULL`; жёсткий `DELETE`
  запрещён политикой (аудит + 152-ФЗ), все выборки фильтруют `deleted_at IS NULL`;
* уникальность — партиальными индексами `WHERE deleted_at IS NULL`, чтобы удалённая
  запись не блокировала создание новой с тем же именем;
* строковые enum'ы — нативные типы PostgreSQL.

### Справочники

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `universities` | вузы | `name` и `name_normalized` уникальны среди живых строк; `external_id` уникален при наличии; GIN-индекс `gin_trgm_ops` по `name_normalized` для поиска похожих |
| `vendors` | вендоры ПО | `name` уникален |
| `it_directions` | ИТ-направления | `name` уникален, `is_active` |
| `it_products` | ПО и лицензии | уникальна пара «название + вендор» (см. ниже про `COALESCE`) |
| `it_products_directions` | связь продукт ↔ направления | составной PK |
| `users` | проекция пользователей Keycloak | `keycloak_id` уникален; `role` — кэш роли из токена |
| `university_contacts` | ответственные со стороны вуза | ПДн: только ФИО, должность, рабочие контакты |
| `university_assignments` | закрепление КАМа за вузом | GiST exclusion: у вуза не может быть двух живых назначений с пересекающимися периодами |

### Основная сущность

`interactions` — карточка «вуз + ИТ-направление + ИТ-продукт». Уникальность тройки
среди живых строк — это и есть бизнес-ключ upsert при импорте.

Индексы: `university_id`, `responsible_user_id`, `license_expires_at`,
`(university_id, it_product_id)`, а также `it_direction_id`, `it_product_id`,
`license_signed_at` — под будущие отчёты (SPEC-03).

`license_expires_at` вычисляется как «дата подписания + срок действия», если явное
значение не передано.

### Импорт

| Таблица | Назначение |
|---|---|
| `import_jobs` | задача импорта: имя файла, sha256, целевая сущность, статус, маппинг, статистика |
| `import_rows` | построчный разбор: сырые ячейки, разобранные значения, статус, сообщения |
| `import_mapping_presets` | сохранённые схемы «колонка файла → поле системы» |

### Аудит

`audit_log` — append-only: bigserial PK, `occurred_at`, `actor_id` / `actor_name`
(денормализовано), `action`, `entity_type` / `entity_id`, `changes jsonb`,
`ip_address inet`, `user_agent`, `request_id`.

### Про `COALESCE` в уникальных индексах

В PostgreSQL два `NULL` никогда не «равны», поэтому обычный уникальный индекс по
колонке с `NULL` не предотвращает дубли. Бизнес-ключ `interactions` и пара
«продукт + вендор» содержат nullable-колонки, поэтому индексы строятся по
`COALESCE(колонка, '00000000-...-000000000000'::uuid)` — так отсутствие значения
ведёт себя как значение. Без этого карточки без направления или без продукта
(а их в каталоге заказчика большинство) плодились бы при каждом импорте.

## Аудит: как это работает

Разработчик не вызывает логирование вручную — этого достаточно, чтобы про него
забыли. Вместо этого:

1. **Кто и откуда** — `contextvars.ContextVar` с `AuditContext`, который
   выставляет middleware один раз на запрос.
2. **Что именно изменилось** — событие SQLAlchemy `after_flush`. Это единственная
   точка, где первичные ключи уже проставлены, а история изменений атрибутов ещё
   цела; ровно это и нужно записи аудита.
3. **Запись** — Core `INSERT` по соединению флаша внутри `SAVEPOINT`. Сбой
   логирования откатывает только savepoint, поэтому упасть основной транзакции он
   не может (требование §5.5); ошибка уходит в application log.

В `changes` попадают **только реально изменившиеся поля**; `created_at`,
`updated_at` и производные колонки `*_normalized` исключены.

Поля с ПДн (`full_name`, `email`, `phone`) **маскируются**: сохраняется факт
изменения и sha256-хеши старого и нового значения, но не открытый текст. Открытые
значения остаются только в таблице самой сущности.

Отдельно логируются `access_denied`, `read_pd`, `export` и `import`.

Таблица защищена от переписывания двумя независимыми слоями: `REVOKE UPDATE,
DELETE` и триггер `BEFORE UPDATE OR DELETE`, который нужен потому, что гранты не
действуют на владельца таблицы и суперпользователя.

## Импорт XLSX

Процесс двухфазный: пользователь обязан увидеть предпросмотр до записи в БД.

| Шаг | Эндпоинт | Что происходит |
|---|---|---|
| 1 | `POST /api/v1/imports` | проверка размера и **реального формата по сигнатуре файла** (имени и `Content-Type` не доверяем), разбор строк, авто-маппинг колонок, предупреждение о повторной загрузке того же файла |
| 2 | `POST /api/v1/imports/{id}/mapping` | пользователь подтверждает или правит маппинг, может сохранить как пресет |
| 3 | `POST /api/v1/imports/{id}/validate` | dry-run: разбор и проверка каждой строки, ничего не пишется |
| 4 | `POST /api/v1/imports/{id}/commit` | запись в одной транзакции |
| 5 | `GET /api/v1/imports/{id}/report` | xlsx с исходными строками и колонкой результата |

Поддерживаемые цели импорта: `interactions` (каталог заказчика), `universities`,
`it_products`, `contacts`.

**Правила валидации:** пустое «Название ВУЗа» → `error`, строка не импортируется;
нераспознанная дата или срок лицензии вне диапазона 1–10 → `warning`, поле остаётся
пустым; ненайденный или неоднозначный менеджер → `warning`, поле пустое, строка
импортируется; дубли внутри файла → `warning`, применяется последняя строка.

**Похожие названия вузов** ищутся в два этапа: trigram-индекс отбирает кандидатов
(дёшево и по индексу), затем кандидаты переоцениваются по редакционному
расстоянию — trigram плохо переносит перестановку одной буквы, а именно так
выглядит человеческая опечатка. Итоговая оценка сравнивается с
`IMPORT_FUZZY_THRESHOLD`. Совпадение только **предлагается** в сообщении; записи
никогда не сливаются автоматически.

**Правила записи:** upsert по бизнес-ключу «вуз + направление + продукт» — дубли не
плодятся; пустая ячейка означает «нет данных» и **не затирает** заполненное
значение в БД; строки со статусом `error` пропускаются, не блокируя остальные;
любая непредвиденная ошибка откатывает всё и переводит задачу в `failed`.

Даты принимаются в виде excel-serial, `ДД.ММ.ГГГГ`, `ГГГГ-ММ-ДД` (а также
`ДД/ММ/ГГГГ` и двузначного года — такие значения встречаются в файлах заказчика).

## Workflow-движок

Карточка взаимодействия едет по маршруту: `workflow` → `версия` → `этапы` → `переходы`.

### Базовый процесс

Эталонный цикл работы с вузом из 14 шагов (`WF-01`…`WF-14`) создаётся при первом
запуске сид-скрипта, публикуется и назначается маршрутом по умолчанию. Он остаётся
редактируемым. Помимо движения вперёд маршрут разрешает вернуть карточку на
предыдущий этап, а шаг «Корректировка документов», отмеченный в ТЗ как
опциональный, можно пропустить напрямую из `WF-04` в `WF-06`.

Новая карточка встаёт на начальный этап автоматически — и при создании через API,
и при импорте каталога.

### Версионирование

Опубликованная версия **заморожена**. Добавить или убрать этап, изменить набор
переходов можно только в черновике: на опубликованной версии вернётся
`409 WORKFLOW_VERSION_LOCKED`. Чтобы изменить действующий маршрут, версия копируется
в новый черновик (`POST /workflows/{id}/versions` с `clone_from_id`), правится и
публикуется; предыдущая уходит в архив, но не удаляется.

Карточка хранит **версию**, на которой стартовала, а не workflow. Поэтому публикация
новой версии не перерисовывает маршрут работы, которая уже идёт: карточка продолжает
резолвить свои этапы и переходы по замороженной версии, даже после её архивации.

Единственное исключение — **переименование этапа**: это разрешено и в опубликованной
версии, потому что `FR-03` требует такой возможности, а сломать ничего не может —
идентификатор этапа не меняется.

### Переходы

Переход разрешён, только если он описан в версии карточки; иначе
`422 WORKFLOW_INVALID_TRANSITION`, и в `details.allowed_stage_ids` перечислено, куда
двигаться можно. Если переход помечен `requires_comment` (по умолчанию — да),
комментарий обязателен; он сохраняется в истории перемещений и попадает в аудит.

`GET /interactions/{id}/route` отдаёт одним ответом всё для отрисовки пути: схему
этапов и переходов, текущее положение, доступные переходы и историю с комментариями.
`GET /workflows/{id}/graph` — то же для маршрута целиком, плюс количество живых
карточек на каждом этапе.

### Вложения к этапам

Принимаются десять форматов из ТЗ: png, jpeg, pdf, zip, gzip, rar, doc, docx, xls,
xlsx. Тип определяется **по сигнатуре файла**, а расширение обязано с ней совпадать —
переименованный `.exe` в `.pdf` не пройдёт. Файлы лежат в базе, отдельной таблицей
от метаданных. Загрузка попадает в аудит как обычный `create`, скачивание — отдельным
событием `export`.

## Права доступа

| Роль | Права |
|---|---|
| `user` | видит только вузы, где он **активный** ответственный в `university_assignments`, и связанные с ними данные |
| `manager` | видит всё, создаёт и изменяет записи, управляет назначениями |
| `admin` | плюс мягкое удаление и доступ к журналу аудита |

Фильтр видимости применяется в **базовом репозитории**, а не в роутере: так его
нельзя случайно забыть. Запрос чужого объекта по прямому ID возвращает `403`, а не
`404` — иначе факт отказа не попал бы в аудит.

## Формат ошибок

```json
{
  "error": {
    "code": "IMPORT_INVALID_FORMAT",
    "message": "Файл не является корректной таблицей Excel",
    "details": {"filename": "catalog.xlsx"},
    "request_id": "0d2f8f3e-1c1a-4a1e-9f2f-6f0b7f1f2a3b"
  }
}
```

Коды: `VALIDATION_ERROR`, `NOT_FOUND`, `ACCESS_DENIED`, `DUPLICATE_ENTITY`,
`IMPORT_INVALID_FORMAT`, `IMPORT_FILE_TOO_LARGE`, `IMPORT_MAPPING_INCOMPLETE`,
`IMPORT_JOB_WRONG_STATE`, `INTERNAL_ERROR`, а также добавленные вместе с
workflow-движком `WORKFLOW_INVALID_TRANSITION`, `WORKFLOW_VERSION_LOCKED`,
`ATTACHMENT_INVALID_FORMAT`, `ATTACHMENT_TOO_LARGE`.

`request_id` возвращается и в заголовке `X-Request-ID`; если клиент прислал свой
корректный `X-Request-ID`, используется он — это даёт сквозную трассировку.

## Точки стыка с другими спеками

* `interactions.workflow_version_id` и `interactions.current_stage_id` — nullable
  UUID **без** внешнего ключа. Таблиц workflow ещё нет; FK добавит SPEC-02
  отдельной миграцией. Логика этой спеки на них не завязана.
* Отчёты (SPEC-03) будут читать `interactions` с джойнами по всем справочникам —
  индексы под фильтрацию по периоду, вузу, направлению, продукту и ответственному
  уже заведены.
* Интеграции (SPEC-04) будут писать в те же справочники, поэтому вся логика
  find-or-create и нормализации названий живёт в сервисном слое
  (`app/services/catalogs.py`, `app/services/text.py`) и вызывается извне, а не
  зашита в парсер Excel.

## Принятые допущения

Спека не покрывает всё; ниже — решения, принятые по принципу «самый
консервативный вариант». **Пункты, помеченные 🔐, касаются персональных данных —
решение по ним принимает заказчик, а не разработчик.**

1. **🔐 Маскирование ПДн в аудите — sha256 без соли.** Спека требует «сохраняем
   факт изменения и хеш». Соль сделала бы хеши несравнимыми между записями и
   убила бы смысл («изменилось ли значение?»), но несолёный хеш телефона или email
   теоретически подбирается по словарю. Если заказчику это неприемлемо — нужен
   HMAC с ключом в секрет-хранилище и отказ от сравнения хешей между записями.
2. **🔐 Список полей-ПДн зафиксирован в коде** (`full_name`, `email`, `phone` в
   `__pd_fields__`). Если заказчик отнесёт к ПДн что-то ещё (например, должность),
   список нужно расширить — это одна строка в модели.
3. **🔐 Сырые строки Excel хранятся в `import_rows.raw_data` бессрочно.** Так
   работают предпросмотр, повторная валидация и отчёт об ошибках без хранения
   самих файлов. Но в этих строках лежат ФИО контактов вуза. Политика ретенции
   (через сколько дней чистить `import_rows` завершённых задач) — вопрос к
   заказчику; автоочистка не реализована сознательно.
4. **🔐 Загруженные файлы на диск не сохраняются** — только их sha256 и разобранные
   строки. Это осознанно уменьшает число мест, где лежат ПДн.
5. **Партиционирование `audit_log` по месяцам не сделано.** Спека называет его
   желательным, но не блокирующим. Партиционированная таблица требует, чтобы
   ключ партиционирования входил в PK, что ломает простой `bigserial`, и
   нуждается в фоновом создании партиций. Индексы `(entity_type, entity_id)`,
   `(actor_id, occurred_at)` и `occurred_at` заведены; переход на партиции —
   отдельная миграция, когда объём это оправдает.
6. **`X-Debug-User` не принимает ФИО.** Значения HTTP-заголовков ASCII-only, а
   кириллическое ФИО туда не помещается. Принимаются UUID, `keycloak_id` и email.
7. **Заголовок должен указывать на существующего сотрудника** — заглушка не
   выдаёт личности сама. Иначе dev-режим стал бы генератором пользователей.
8. **Нормализованные копии названий хранятся в колонках** `name_normalized` /
   `full_name_normalized`, а не считаются выражением в индексе: импортёру нужно
   читать их обратно, а trigram-поиск обязан работать по той же свёртке.
   Поддерживаются сервисным слоем, из diff-ов аудита исключены.
9. **Уникальность вуза проверяется и по `name`, и по `name_normalized`** — первое
   буквально по спеке, второе строже и реально ловит «МГТУ» против «мгту».
10. **У вуза один активный ответственный.** Спека формулирует ограничение как «у
    вуза не может быть двух активных назначений с пересекающимися периодами», то
    есть про вуз, а не про пару «вуз + сотрудник». Реализовано именно так:
    exclusion-ограничение по `university_id`.
11. **`DELETE /assignments/{id}` закрывает период сегодняшней датой** и возвращает
    обновлённую запись (`200`, не `204`) — чтобы клиент сразу увидел
    проставленный `assigned_to`.
12. **`import_rows` удаляются жёстко** при повторной валидации задачи: это
    черновик предпросмотра, а не бизнес-данные. Политика мягкого удаления на них
    не распространяется.
13. **Импорт создаёт справочники по мере надобности** (find-or-create для вуза,
    вендора, продукта, направления, контакта). Спека предписывает это для вуза,
    вендора и ПО; для направления и контактов применено то же правило.
14. **Контакты из колонки «Ответственные от ВУЗа» привязываются к вузу**, а не к
    карточке взаимодействия: в модели данных контакты принадлежат вузу.
15. **Неоднозначное ФИО менеджера трактуется как «не найден»** — если свёртка ФИО
    совпала с несколькими сотрудниками, выдаётся `warning`, поле остаётся пустым.
    Молча выбрать одного из двух однофамильцев хуже, чем не выбрать никого.
16. **Роль берётся из realm-ролей Keycloak** (`realm_access.roles`), выбирается
    сильнейшая из известных; при отсутствии — `user`. Точный маппинг ролей
    заказчика на `user` / `manager` / `admin` уточняется при подключении Keycloak.
17. **Локальная проекция пользователя обновляется из токена при каждом входе** —
    Keycloak остаётся мастером, расхождения ФИО и роли устраняются автоматически.
18. **Список сотрудников и карточка сотрудника доступны всем ролям**: без этого
    невозможно выбрать ответственного в интерфейсе. Создание сотрудника вручную —
    только `admin`.
19. **Расширения `pg_trgm` и `btree_gist` создаются миграцией.** Пользователь БД
    должен иметь на это право (в managed-инсталляциях их иногда нужно включать
    заранее).
20. **Сортировка по неизвестному полю — ошибка `422`, а не молчаливое
    игнорирование**: незаметно проигнорированная сортировка выглядит как сломанная
    пагинация.
21. **`29 февраля + N лет` округляется до 28 февраля** при вычислении окончания
    лицензии — иначе дата просто не существует в невисокосном году.
22. **Опубликованная версия workflow заморожена, переименование этапа — нет.**
    Спека требует и «корректировки именования статусов» (`FR-03`), и того, чтобы
    правка маршрута не переписывала путь карточек в работе (A6). Это разные
    операции: переименование меняет ярлык и идентификатор этапа не трогает,
    поэтому разрешено в опубликованной версии; всё структурное требует черновика.
23. **Вложения хранятся в базе, а не на томе или в объектном хранилище.**
    Самый консервативный вариант под 152-ФЗ: одно место для защиты, один бэкап,
    который не может разойтись с метаданными, и никакой дополнительной
    инфраструктуры. Байты лежат в отдельной таблице, чтобы список вложений их не
    тянул. Если объём вырастет — переезд в S3 затрагивает только
    `WorkflowAttachmentRepository`. **🔐 Срок хранения вложений заказчик пока не
    определил, автоочистки нет.**
24. **Мягкое удаление вложения не стирает байты** — физическая очистка это вопрос
    политики хранения, а не кнопки «удалить».
25. **В базовом маршруте есть возврат на предыдущий этап.** В ТЗ перечислены только
    14 шагов вперёд, но без обратного перехода единственным способом исправить
    ошибку был бы новый workflow. Шаг `WF-05` («Корректировка документов»), отмеченный
    в ТЗ как опциональный, можно пропустить переходом `WF-04 → WF-06`.
26. **Комментарий при переходе обязателен по умолчанию**, но управляется флагом
    `requires_comment` на самом переходе: `FR-03` требует комментирования, при этом
    для части переходов он не несёт информации, и заказчик сможет их ослабить без
    правки кода.
27. **История перемещений и вложения несут денормализованный `university_id`.**
    Фильтр видимости работает по колонке вуза; копия позволяет применить его
    напрямую, не присоединяя `interactions` в каждом запросе.
28. **Контакт создаётся как подресурс вуза** — `POST /universities/{id}/contacts`,
    а не `POST /university-contacts`: контакт не существует без вуза. Остальные
    операции (список, чтение, изменение, удаление) доступны по плоскому пути
    `/university-contacts/{id}`, как и для прочих справочников.
29. **Сотрудники (`/users`) добавлены сверх перечня §7** — без них нельзя ни
    назначить ответственного, ни узнать собственную роль (`/users/me`).
30. **Справочник нельзя мягко удалить, пока на него ссылаются живые записи** —
    запрос возвращает `422 VALIDATION_ERROR` со списком того, что мешает.
    Спека этот случай не описывает. Мягкое удаление связанной записи не убрало бы
    её с глаз: она продолжила бы всплывать вложенным объектом внутри каждой
    ссылающейся карточки. Блокировка повторяет уже объявленный на внешних ключах
    `ON DELETE RESTRICT`, ничего не теряет и обратима — в отличие от каскадного
    удаления.
31. **`license_expires_at` пересчитывается только при изменении своих входов.**
    PATCH, не трогающий дату подписания и срок, не трогает и дату окончания —
    иначе правка комментария молча заменяла бы вручную введённую дату вычисленной.
    По той же причине импорт не обнуляет сохранённую дату окончания, если в файле
    нет ни даты подписания, ни срока.
